# OmniCommit 会议 Web 服务

本服务将网页和导出的 OmniCommit 模型部署在同一台 GPU 服务器。第一版网页支持麦克风、电脑系统声音和本地音视频文件。开始会议前，在「音频来源」下找到「音频块时长」。你可以从下拉列表选择常用步长，也可以直接输入整数毫秒数。例如，输入 `200` 并点击「开始转录」，服务按每轮 0.2 秒处理新增音频，页面显示 `WAIT` 或 `DIRECT` 对应的新增转录、语种和说话人。本场结束后可以更改下一场的步长。页面提供逐段修正、说话人合并或改名，以及 TXT / JSON 导出。

**当前不要求网页访问口令。** 以下所有服务器路径和 GPU 编号都是示例，请替换为实际路径和设备。启动命令直接填写路径，与 FLEX 的使用风格一致。

## 1. 启动前准备

- 模型应是已完成 SFT 和导出的 **HF 模型目录**，不是 MCore 训练目录或单独的 LoRA checkpoint；目录需包含导出产生的 `omnicommit_tokens.json` 和匹配的 tokenizer、权重。模型必须使用与训练相同的 token 和 ID。
- 在已有的 FLEX 推理环境中运行，vLLM 后端目标版本为 0.11.1；保留原来的 torch、CUDA 和 Transformers 依赖。服务需能导入 FastAPI、Uvicorn、NumPy、soundfile、scipy；文件模式还需服务器上的 FFmpeg。
- 当前示例数字模式为 `normalized`，必须与训练数据使用的数字格式相同。模型只处理文本转录，不输出语音。
- 以下 `rolling` 是**实验性启发式裁剪**：它可能丢失长时间尚未提交的语音。当前尚无真实模型、真实会议的 30 分钟稳定性和说话人准确率验收，不能视为已保证。
- 连续 WAIT 且无法推进待提交边界时，默认待提交/上下文预算为 30 秒；达到上限会明确停止会话。不能简单增大秒数冒充长会议已解决，还需同时满足模型 4096 token 上下文预算。

```bash
cd /data/yb/Code/OmniCommit
ffmpeg -version
```

## 2. 用 vLLM 启动

在已有 FLEX 推理环境中执行，直接填写导出的 HF 模型路径：

```bash
cd /data/yb/Code/OmniCommit

bash start_server.sh /data/yb/Code/OmniCommit/models/omnicommit-merged
```

默认监听 `0.0.0.0:18889`，使用 vLLM、`normalized` 数字格式和 `rolling` 上下文。按默认配置启动，网页显示 500 ms，可输入 200 至 5000 之间的任意整数。输入框旁显示当前服务允许的范围。例如，要试 80 ms，可给启动命令追加 `--chunk-seconds 0.08`，此时页面默认值和下限都是 80 ms。未指定时长的旧客户端沿用启动默认值。自动说话人参照默认关闭，网页仍支持人工参照和修正。

默认 `--max-sessions 1`，模型请求通过单个 worker 串行处理。检查服务是否就绪：

```bash
curl http://127.0.0.1:18889/health
```

服务启动后，在同一内网的浏览器访问：

```text
http://服务器内网IP:18889
```

网页不需要输入令牌。浏览器采集麦克风和系统声音仍需要受信任的 **HTTPS 或 localhost**；远程内网 IP 的普通 HTTP 页面不能绕过浏览器限制。音视频文件模式可在浏览器支持时使用普通 HTTP。

例如已有证书时，用以下完整命令启用 HTTPS：

```bash
bash start_server.sh /data/yb/Code/OmniCommit/models/omnicommit-merged \
  --ssl-certfile /实际路径/server.crt \
  --ssl-keyfile /实际路径/server.key
```

使用 `https://与证书匹配的地址:18889` 访问。证书必须被浏览器信任，并与实际访问地址匹配；如使用 IP 访问，证书也需匹配该 IP。服务没有口令认证，请按实际网络环境控制访问范围。

## 3. 三种音频来源

1. **麦克风**：在页面选择“麦克风”，点击开始并授权浏览器使用设备。
2. **电脑声音**：选择“电脑声音”，在浏览器共享对话框选择有声音的来源并勾选共享音频；可以选择同时采集麦克风。可共享的系统声音取决于浏览器和操作系统。
3. **音视频文件**支持整段和指定区间。选好文件后，可以填写开始、结束时间，再点「开始转录」。两个时间都留空会处理整份文件，只填开始时间会从该位置处理到文件末尾，只填结束时间会从文件开头处理到该位置。第一版和 Second 的操作相同。

例如，要单独验证 **58 秒到 1 分 36 秒**的德语，把开始时间填为 `58`、结束时间填为 `1:36`，音频块时长选 `500` ms。浏览器从 58 秒播放，模型从空历史开始听。到 96 秒会自动处理尾部并结束。完整跑完会有 76 个音频轮次，再加一个结束事件。起点也可以选 `58.23` 这类不在 500 ms 网格上的时间，当次分块从所选起点重新计算。说话人编号属于各自的会话。

要检查前面日语的影响，可以对同一份文件再开一场，开始时间填 `0`，结束时间仍填 `1:36`，在日志里按**原文件时间**比较相同音频区间。运行中点「结束并处理尾部」会处理到当前播放位置。要换起点，请结束当前会话，修改区间后重新开始。文件仍会完整上传并解码，模型逐块接收所选范围内已播放的音频。

文件音轨先保留解码后的源采样率，按当前释放位置截取后再逐块重采样到 16 kHz。测试覆盖 WAV 边界后修改不会改变前一块；压缩编码本身可能存在解码前瞻，音画起始偏移和逐块重采样边界效果仍需用实际文件验证。

页面显示已处理时长、待处理积压、每轮模型及服务耗时。现场积压超过限制时，页面会停止采集并处理已接收的音频。结束时会处理尾部并发送 `<end_of_audio>`。实时转录区可导出正文 TXT，也可导出包含事件和修正结果的 JSON。

文件上传当前限制为 1 GiB、解码音频不超过 4 小时；上传文件和转换后的临时音频在会话结束后清理。此限制不是对 4 小时实时运行或识别质量的保证。

### 回看和下载逐轮日志

展开逐轮日志即可查看模型轮次和 WAIT、DIRECT 计数。默认视图只显示模型轮次，可单看 WAIT、DIRECT，或切到全部事件核查服务状态。页内可翻回较早记录，跳到开头或最新记录。阅读历史时可以保持当前位置，需要连续看新结果时再开启自动跟随。文件播放产生的 `file_wait` 只表示还在等播放器释放音频，只有模型实际返回的 WAIT 才计入轮数。

日志面板默认展开，下载按钮位于会议选择框旁。会话进行中即可下载截至当前的记录，结束后也可从历史会话下载。筛选条件和当前页码只影响阅读。“看最新”只跳转一次；勾选“跟随最新”才会连续滚动。手动关闭跟随、往上滚动或点开某轮详情后，可以停在该处继续读。

排查语种切换时，先看最后一次 DIRECT 的音频位置、归属和后续连续 WAIT 的时长。文件会话在 `ready.file_start_seconds` 和 `ready.file_end_seconds` 记录按源采样点确定的实际范围，逐轮结果用 `source_start_seconds` 和 `source_end_seconds` 记录送入的原文件区间，`start_seconds` 和 `end_seconds` 从本次会话的零秒起算。用播放器时间减去最近的 `source_end_seconds` 可以看出积压了多少秒。服务出错时，`source_heard_seconds` 是原文件中最后成功处理到的位置。反复收到的 `file_wait` 和结束轮的 WAIT 都不增加连续等待的音频秒数。

默认启动脚本使用 rolling 策略，最近音频窗口目标为 12 秒，每次 DIRECT 后按该轮音频终点减去 2 秒估计提交边界，连续 WAIT 期间这个边界不前进。举例来说，最后一次 DIRECT 在 32 秒结束且没有人工确认时，提交边界是 30 秒；持续 WAIT 到 60 秒后，再送 0.5 秒会超过 30 秒的待提交预算并结束会话。全程的 `heuristic_eviction` 表示曾经发生过启发式裁剪，各轮的 `evicted_this_turn` 和窗口里的“本轮裁剪”可以定位具体音频块。人工确认只适用于已核对完整提交的区间。

- **逐轮 TXT** 包含这次会话全部模型轮次，可直接阅读 WAIT、DIRECT 及其输出。
- **日志 JSONL** 按接收顺序保存完整事件，每行一个 JSON 对象。模型结果保留动作、文字、音频时间、耗时和归属字段。文件播放状态、服务错误和人工修正也可在日志中查到。需要核查模型原本输出的说话人时，请查看模型结果行中的 `segments`。网页收到错误事件时会保留错误信息。

日志保存在当前浏览器的 IndexedDB，只记录事件和文本。刷新页面后，用同一浏览器配置访问同一地址即可回看已写入的会话。不同域名、协议或端口的存储相互独立。浏览器清理站点数据、隐私窗口关闭或浏览器回收存储空间都可能使历史记录丢失。若页面提示本地存储不可用，请在关闭或刷新前下载当前会话日志。需要长期分析的会议，可在会后将 JSONL 保存到实验目录。此功能不保存会议音频。

同场会议有参考转录时，可用下载的 JSONL 运行现有评测。若参考文件含多条会议，请加上 `--id` 选择对应记录。模型结果用于计算延迟、字符错误率和说话人归属，各类播放状态和人工修正不计入模型指标。

```bash
python tools/evaluate_stream.py \
  --reference reference.jsonl \
  --predictions meeting-log.jsonl \
  --output meeting-report.json
```

## 4. 说话人修正

页面支持逐段修改归属、合并说话人，以及设置显示名称。修正单段只改变该段；合并通过页面身份映射展示并影响后续显示。受影响的声音参照会被清理，避免明显错误的参照继续参与推理。

模型已收到的历史回复不会因为页面修正被改写；未来模型内部输出的编号仍可能错误。会话结束后修正只影响页面和导出结果，不再修改已关闭会话的模型上下文。

## 5. 可选：实验性自动说话人参照

不加下列参数时自动参照关闭。启用后，服务会在后台尝试用 Qwen3-ForcedAligner 对**已听到的音频**和转录进行对齐，选择候选声音片段作为参照；失败时自动参照在该会话中停用，转录仍继续。参照属于 **experimental / 未核验**，不是可靠的说话人身份确认。

Qwen 只对给定转录估计位置，**不验证转录正确、不检测重叠发言，也不验证说话人身份**。当前实验适配支持中文、英文、日文、韩文、德文、法文、俄文、葡萄牙文、西班牙文和意大利文；阿拉伯语、泰语不会建立此类自动参照。候选是否改善跨时段身份一致性必须用真实模型和会议单独比较，不能从开关状态推断准确率。

`qwen-asr==0.0.6` 依赖 Transformers 4.57.6，而现有 FLEX 推理环境使用 4.57.1；**不要安装到 FLEX/vLLM 环境中**。请使用独立的 Python 3.11 环境，预先准备适配服务器 CUDA 的 torch、所需模型权重，再在该独立环境中安装对齐依赖：

```bash
/data/yb/envs/qwen-align/bin/python -m pip install \
  -r /data/yb/Code/OmniCommit/requirements-alignment-qwen3.txt
```

该环境和模型目录需要预先存在，不能把示例路径当成实际环境。启用实验性参照的完整启动命令：

```bash
bash start_server.sh /data/yb/Code/OmniCommit/models/omnicommit-merged \
  --auto-reference-model /data/yb/models/Qwen3-ForcedAligner-0.6B \
  --auto-reference-python /data/yb/envs/qwen-align/bin/python \
  --auto-reference-device cuda:0
```

对齐模型独立进程、懒加载并在后台处理；请求默认最多等待 120 秒（包含首次加载），可用 `--auto-reference-timeout` 调整。**进程隔离不等于 GPU 资源隔离**，如果与 vLLM 使用同一张卡仍可能争抢显存和算力。应根据实际 GPU 资源选择设备并测量。自动对齐产生的边界不自动成为可信的音频已提交边界。

## 6. 验收

先用短音频验收三种来源、WAIT / DIRECT、结束尾部、语言和说话人修正、TXT / JSON 导出；再用至少 30 分钟真实会议检查文字遗漏和重复、数字与人名、跨语言、A 长间隔后再次出现时的编号，以及推理耗时和音频积压。

对同一音频分别测试关闭和启用实验性参照，比较结果；需要同时核查错误合并、错误拆分和缓存污染。0.5 秒是输入步长，不保证每轮推理耗时小于 0.5 秒。合成音频或 replay 的 30 分钟贯通测试仅验证代码和协议，**不能证明真实模型的识别准确率、实时速度或会议稳定性**。
